# JLU Booking v2.4 动态候选实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把自动预约升级为七档时间优先级、07:32 开放探测和“每次明确失败后立即重新查询”的动态候选轮次，同时保持最终提交结果未知时立即停止的安全语义。

**Architecture:** 配置层负责一次性迁移并持久化七档时间；领域辅助函数负责候选标识、稳定排序和错误分类；单线程状态机区分预热、尚未开放探测、开放后动态轮次及全天捡漏。所有 HTTP 请求继续复用现有 `requests.Session`，请求耗时日志继续独立保存。

**Tech Stack:** Python 3.10+、requests、pytest、Tkinter、JSON、setuptools

**Spec:** `docs/superpowers/specs/2026-09-16-v2.4-dynamic-candidate-design.md`

## Global Constraints

- 不修改四账号的 systemd service/timer 架构，不增加多线程或跨账号限流器。
- 保留 `freeBuyPlace` 请求发出后结果不确定即停止的安全策略；不得自动重试最终提交。
- Token、完整学工号和请求参数不得写入新增日志或状态文件。
- 核心间隔是服务器响应后的 `0.1` 秒，不承诺完整请求周期为 `0.1` 秒。
- `jlu_booking/api.py` 仅在现有异常边界无法表达状态机需求时才修改；默认不改。
- 工作树中的 `start.sh` 删除是用户已有改动，本计划的任何提交都不得包含、恢复或覆盖它。
- 每个任务先写失败测试、运行并确认失败，再写最小实现、运行目标测试，最后提交该任务涉及的文件。

- [ ] **Step 5: 用显式运行状态替换 `warm_candidate` 流程**

`run_booking_loop()` 初始化并维护：

```python
open_detected = False
locked_target = None
attempted_this_round = set()
round_number = 0
attempt_number = 0
```

实现以下转换：

- 预热只 query、排序、输出最高候选，不保存跨阶段候选。
- 首次进入 core 必须令 `locked_target = None` 并立即 query。
- 尚未开放时，query 后锁最高候选；`not_open` 和 `canBook` 传输异常都保持锁定，按阶段间隔重试。
- 第一次明确 `ServerResponseError`（但不是 `not_open/auth/daily/rate`）将 `open_detected` 单向设为 `True`，记录 `OPEN_DETECTED`，将失败键加入 `attempted_this_round`，随后不 sleep 直接 query。
- 进入 salvage 时强制 `open_detected = True`，清锁、清集合并开始新轮次。

- [ ] **Step 6: 实现开放后的动态轮次**

开放状态下每次 query 后执行：

```python
candidates = sort_booking_candidates(available_slots)
eligible = [
    slot for slot in candidates
    if candidate_key(slot) not in attempted_this_round
]
```

若 `eligible` 非空，选择第一项，递增 `attempt_number` 并尝试；明确失败时把键加入集合并立即继续 query。若为空：记录 `ROUND_END`，sleep 当前阶段间隔，清空集合、递增轮次并记录下一次 `ROUND_START`。query 传输异常不修改集合；限流使用 `max(5.0, interval)`。

对于已开放后的偶发 `not_open`，保持当前目标并等待当前阶段间隔，不把目标加入集合，也不把 `open_detected` 改回 `False`。

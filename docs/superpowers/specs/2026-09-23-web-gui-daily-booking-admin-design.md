# Web 工作台、每日自动预约与管理员界面设计

## 目标与范围

在现有 FastAPI/Jinja、SQLite 和独立调度器之上完成网页版第二阶段。普通用户完成注册、Token 激活并登录后，进入以 `jlu_booking/gui.py` 的功能和信息层级为准的响应式工作台；可真实查询场地、经明确确认后手动提交预约、创建一次性任务，以及配置每日自动预约。管理员登录后直接进入独立后台，管理用户、任务和审计记录。两类账号始终使用现有角色授权，不新增管理员代用户预约能力。

本次保留 `jlu_booking.auto` 的 PREHEAT、07:29:57–07:33 CORE、严格候选优先级、异常处理和 07:33 hard deadline。桌面 GUI、CLI、现有一次性任务、加密 Token、同行人、审计机制继续工作。开发和自动化测试不得调用真实预约接口，也不得产生真实预约。部署另行进行，只从已提交并验证的版本更新服务器。

用户已确认：关闭每日开关取消当天尚未开始的每日任务；网页场地查询必须读取真实空闲数据；手动真实预约也要支持；每日任务超过 10 个名额时按开启时间先到先得；截图只作视觉参考，功能以 `gui.py` 为准。

## 方案选择

选择在现有 Web 适配层内增量扩展：Jinja 模板和少量原生 JavaScript 构建响应式页面，Web 端复用 `api.VENUES`、`resolve_venue_sport`、`query_courts` 和 `extract_available_slots`，每日计划生成现有 `booking_tasks`，交给原调度器和 worker。这样保持单服务器、单数据库和既有安全边界。

未选整体改成前后端分离 SPA，因为会引入构建和部署体系并扩大变更面；未选浏览器直连学校接口，因为浏览器端 Token 暴露、跨域限制及无法可靠处理后台调度。

## 页面与访问控制

- 登录成功后，普通活跃用户进入 `/` 的用户工作台；管理员进入 `/admin`。首次改密及 Token 激活流程仍先完成，之后进入各自首页。管理员访问 `/` 也应跳往 `/admin`，普通用户访问 `/admin/*` 继续按现有规则拒绝。
- 用户工作台以桌面 GUI 的“场地查询”和“自动预约”为两项主导航。场馆选择是两项功能共享的页面状态；场馆和可选项目均由 `api.VENUES` 提供，切换场馆立即更新项目选项。
- 场地查询页包含场馆、项目、今天/明天、查询按钮、场馆/日期/场地数/空闲时段数摘要以及按场地分组的空闲时段。结果标注查询时间和目标日期，不把旧查询结果当作当前状态。
- 自动预约页展示 Token 与同行人准备状态、当前任务与最近结果、一次性预约入口，以及一份“每日自动预约”配置。配置字段沿用 GUI：场馆、项目、执行日的当天/次日、已验证同行人、首选场地号、按顺序排列的时间优先级、仅扫描/真实预约。真实预约必须显式选择并确认，不因默认值或网页改版自动开启。
- 桌面尺寸使用 GUI 的蓝色侧栏和卡片信息层级；窄屏改为可折叠导航和单列卡片，控件保持可点击与键盘可用。网页不复制 Tkinter 的窗口外框或本机文件路径。
- 管理员有独立的后台导航与概览，复用已有用户列表/详情、启停账号、密码重置、任务列表、审计及重新验证后限时查看 Token 的服务端权限。普通用户页面不出现管理员操作，管理员首页不混入普通用户工作台。

## 每日自动预约模型

新增每用户至多一条每日计划，保存配置快照、启用状态、`enabled_at`、更新时间和最近物化状态。首次创建默认关闭。每次从关闭改为开启时重置 `enabled_at`；持续开启期间修改配置不改变排队顺序。Token 或同行人失效、用户被禁用时，不生成任务，页面给出具体阻止原因，但不泄露敏感值。

每日计划并非长期运行的 worker。独立调度器在北京时间当天 07:27 前，把符合条件的计划物化为当天 `booking_tasks` 的一条 `scheduled` 记录，随后仍由现有 07:27–07:29:57 启动窗口运行。启用操作在截止前也尝试立即物化，以免临近 07:27 时仅靠下一次调度 tick 而错过。07:27:00 起不再为当天新建任务，下一次可执行日为次日。每次物化和名额计数放在 SQLite `BEGIN IMMEDIATE` 事务中；同一用户、同一执行日、同一计划绝不能重复生成。重启后重新协调计划与任务，不重复启动或提交。

每天最多 10 个自动任务，包含一次性和每日物化任务。已接受的一次性任务先占其执行日期名额；剩余名额分给已开启的每日计划，按 `enabled_at` 升序、用户 ID 打破同一时间平局。超过名额的计划可以保持开启作为候补，页面明确显示“已开启、当天未获得名额”，不能显示成已排程。截止前有人关闭并释放名额时，下一次协调可按顺序补位；截止后不补建当天任务。当天已有一次性任务的用户不再额外物化每日任务。启用每日计划若已有当日一次性任务，仍保存计划，下一次无冲突的执行日再运行。不能因为一次性任务或每日计划而突破现有每用户最多一个 `scheduled/running` 任务的约束。

关闭每日开关是原子操作：先把计划设为关闭，再取消由该计划产生且仍为 `scheduled` 的任务，包括 07:27 后尚未被调度器认领的任务；已经 `running`、已发出请求或已有终态的任务不撤销、不终止，只停止未来日期的物化。这里仅为“关闭每日计划”增加按任务实际状态判定的取消路径；原一次性任务 07:27 后冻结规则保持不变。07:27 前编辑每日配置时，尚未开始的当日每日任务同步更新快照；07:27 起编辑只影响下一执行日，运行中任务维持已冻结配置。界面显示精确执行日期、目标日期和北京时间状态。

## 真实查询与手动预约

只允许已登录的活跃普通用户使用查询和手动预约。服务器以该用户的加密 Token 解密值调用学校接口；Token 不发往浏览器、不进入查询 URL、HTML、普通 JSON 或日志。查询输入在服务端校验场馆/项目对应关系与今天/明天日期，调用现有 `query_courts` 并用 `extract_available_slots` 整理结果。设置按用户的查询限流和请求超时；查询等待不阻塞 FastAPI 事件循环，也不改变独立自动 worker 的 CORE 速度。

服务端把每次查询的候选快照与所属用户、目标日期、创建时间保存两分钟；到期必须重新查询。页面只提交不透明候选 ID；确认时从当前用户的未过期快照读取场馆、项目和时段，不能信任浏览器回传的场地、价格或 Token。点选时段后展示已验证同行人及目标详情，并调用 `canBook` 做预检。预检通过仍不提交；只有用户明确点“确认真实预约”时，服务端在防重复保护下再次 `canBook`，随后调用 `freeBuyPlace`。预检与最终提交均以学校实时结果为准，不依赖旧查询快照的可用性判断。

手动提交有独立的持久化尝试记录和不可重复使用的确认凭证。服务端在真正提交前原子记录“提交中”，同一用户同时只允许一个提交；重复点击、浏览器重试或 Web 进程重启不会再次发送 `freeBuyPlace`。学校明确成功时保存成功结果并阻止同一用户同一目标日期的重复自动/手动提交；学校明确拒绝时保存失败原因，允许用户重新查询后重新选择；提交已发出但网络中断、解析失败或进程死亡时标记“结果不明”，禁止盲目重试，提示到学校系统核对。Web 进程重启时遗留的“提交中”记录按结果不明处理，不自动重放。页面状态与日志使用脱敏文字。

同一账号已有运行中的自动任务时，不允许并行手动提交。手动提交与调度器认领之间使用数据库中的账号级提交保护，避免两条路径同时对同一个 Token 下单；已有自动成功或结果不明时，同一目标日期的手动提交也被阻止。手动成功或结果不明时，尚未开始且目标日期相同的自动任务不得再启动。手动预约不占“每天 10 个自动任务”的服务器队列名额，但仍遵守学校接口自身的预约上限与明确限流。普通网页查询有独立限流，不向 CORE 加入人为 sleep、cooldown 或排队。

## 错误与安全边界

HTTP 429、明确频率限制、ACCOUNT_BLOCKED、Token 失效、当日上限、候选失效、普通服务器拒绝、网络错误和 `BookingOutcomeUnknown` 分别映射为可理解的网页状态；普通错误不泄露学校接口原始响应或密文。任何提交结果不明都优先安全停止。同一用户只能查看自己的候选、提交尝试、计划和任务；管理员继续通过现有受审计权限查看用户及结果。所有修改端点保留 CSRF，秘密响应 `no-store`。时间均以 `ZoneInfo("Asia/Shanghai")` 判定，不依赖服务器系统时区。

SQLite 使用有版本号的增量迁移；不改写现有用户、密钥或历史任务。新增表和索引需支持计划幂等物化、手动确认凭证一次性使用、按用户/日期防重复。对缺失快照、过期确认、被禁用用户、失效 Token 和数据库繁忙给出明确失败，不进行后台隐式提交。

## 验证与交付

自动化测试仅用假学校接口和临时 SQLite，断言真实请求函数不会访问公网。覆盖按角色首页跳转与越权拒绝、GUI 选项和移动端导航、查询参数与候选所有权、手动预检与最终确认分离、重复提交/结果不明/进程恢复、每日配置与启停边界、先到先得及一次性任务占额、计划物化幂等、07:27 后关闭尚未开始任务、管理员现有能力、CORE 行为回归。验证运行完整 `python -m pytest`、`python tools/privacy_check.py`、`python -m compileall -q jlu_booking`、`git diff --check`。本地验证完成后提交代码；服务器更新属于后续独立部署步骤，不在本设计开发阶段直接修改现有服务器服务或真实预约状态。

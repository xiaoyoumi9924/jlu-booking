# v2.4.1 Reliability Design

## Goal

Make unattended booking safe and observable by preventing repeated attempts against stale court results, limiting all-day traffic, logging the court that is actually submitted, validating Tokens before replacement, and recording a stable last-run status.

## Candidate lifecycle

The booking loop keeps two distinct kinds of memory:

- `attempted_this_round`: transient deduplication for the current fast booking round.
- `invalidated_candidates`: candidates that produced an explicit `target_unavailable` response and must remain blocked while the query endpoint continues to advertise them.

An invalidated candidate is keyed by court short name, start time, and end time. It remains blocked across core, closing, and salvage phases in the same run. A successful query that no longer contains the key marks that candidate as absent. If a later successful query contains the key again, the candidate is considered genuinely reappeared and becomes eligible. Query failures and malformed responses never count as disappearance.

Only `target_unavailable` invalidates a candidate. Generic server rejection, rate limiting, authentication errors, and transport failures have separate handling and never poison the lifecycle set.

## Phase behavior

- Warmup remains query-only.
- Before opening, `not_open` keeps the best candidate locked and retries after the phase interval.
- After opening, explicit candidate failures immediately release the lock and refresh the query.
- Core and closing may walk the current eligible candidate set quickly, with per-round deduplication.
- Salvage performs one scheduled query every 10 seconds and at most one booking attempt per tick. A `target_unavailable` result may trigger one immediate read-only refresh to reconcile the lifecycle, but never another submission in the same tick.
- After opening, rate limiting and precheck transport failures release the lock; after the backoff the program queries fresh state. A final submission with unknown outcome still stops immediately.

## Logging

Console and event logs distinguish server visibility from actual submission:

```text
QUERY | visible=22 | invalidated=17 | eligible=5
TRY | round=3 | attempt=2 | target=羽毛球6 15:30-17:30 [ymq6]
RESULT | target_unavailable
REFRESH | immediate
```

The target printed by `TRY` must be the same slot passed to `attempt_real_booking`. Salvage suppresses repetitive query chatter and emits state changes, real attempts, outcomes, and periodic summaries. No Token, full request URL, or full student number may be logged.

## Token validation

A shared read-only validator returns one of three results:

- `valid`: the school query endpoint accepted the Token.
- `invalid`: the school explicitly reported an authentication failure.
- `unavailable`: timeout, TLS/transport error, HTTP 5xx, malformed response, or an unclassified server rejection.

`jlu-booking-token set` validates before writing. Only `valid` replaces the saved Token; `invalid` and `unavailable` preserve the previous file. `jlu-booking-token verify` checks the effective Token source, including environment-variable precedence, without displaying the secret.

The GUI uses the same validator and never deletes the previous Token because of a network failure. Interactive automatic runs also validate before saving. Scheduled runs validate at startup and write a stable `TOKEN_CHECK` event.

## Runtime status

The automatic task writes an atomic, privacy-safe `last_run.json` under the runtime state directory. Supported statuses are `starting`, `running`, `success`, `no_result`, `token_invalid`, `network_unavailable`, `daily_limit`, `submission_unknown`, `stopped`, and `error`.

`jlu-booking-status` reads that file and prints a concise explanation. It is a project-level status command; server-specific inspection of multiple systemd accounts remains an operations concern.

## Compatibility and safety

- Python remains 3.10+ and no new dependency is added.
- The same `requests.Session` remains in use; no speculative cache-busting parameter is added.
- Token storage remains atomic and outside the repository.
- Existing successful-booking state and unknown-final-outcome safeguards remain unchanged.
- Documentation for GUI, CLI, and all three automation platforms is updated.

## Acceptance criteria

1. A candidate returning `target_unavailable` is submitted once even if 100 later queries still advertise it.
2. The same candidate becomes eligible only after a successful query omits it and a later successful query returns it.
3. A new candidate can be attempted while an invalidated candidate remains visible.
4. Salvage performs at most one booking attempt per 10-second tick.
5. Console `TRY` output names the slot actually submitted.
6. Invalid or unverifiable replacement Tokens never overwrite the previous saved Token.
7. GUI, CLI, and automatic startup share the same three-way Token result.
8. Logs and status files contain no Token or full student number.

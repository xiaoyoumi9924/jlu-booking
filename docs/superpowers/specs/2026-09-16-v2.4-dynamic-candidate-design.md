# JLU Booking v2.4 动态候选与开放检测设计

日期：2026-09-16

## 目标

v2.4 根据 2026-09-16 的真实运行日志修正三个问题：

1. 完整覆盖学校返回的七个常见时间段，并在所有时间段内正确执行首选场地优先。
2. 预约真正开放后，每个候选明确失败都立即重新查询最新状态，不继续使用旧候选列表，也不被查询接口的短暂缓存困在同一场地。
3. 把 07:32 左右的“尚未开放探测”和开放后的“动态候选轮次”分成两套明确策略，并留下可以直接分析开放时刻的事件日志。

本次不增加多线程、跨账号通信、永久黑名单、候选冷却时间或“查询我的预约”接口。四个账号继续使用独立 Token、配置、日志、状态文件、systemd service 和 timer，只共享同一套 Python 代码。

## 配置与迁移

默认时间优先级改为：

1. `17:30-19:30`
2. `15:30-17:30`
3. `19:30-21:30`
4. `10:00-12:00`
5. `13:00-15:30`
6. `07:30-10:00`
7. `06:00-07:30`

加载旧配置时采用兼容迁移：

- 配置恰好等于旧版四档默认值时，直接升级为上述完整七档顺序。
- 配置包含用户自定义顺序时，保留原有顺序，再按新默认顺序补齐缺失的标准时间段。
- `load_auto_config()` 检测到标准化结果与磁盘内容不同时，立即通过现有原子写入逻辑保存迁移后的完整结果，因此每个账号只需迁移一次。
- 学校以后返回未知时间段时，不修改配置文件；未知时间段在所有已配置时间段之后参与候选排序。

`config/auto_booking.example.json`、GUI 展示、命令行摘要和使用文档同步使用完整七档。

## 候选排序

新增一个统一的候选排序函数，早上抢票和全天捡漏都调用它。排序函数返回完整的新列表，不修改接口原始结果。

候选唯一标识为：

```text
(place_short_name, start, end)
```

单次运行的日期、场馆和项目固定，因此不需要重复放入候选标识。若 `place_short_name` 缺失，该候选不能提交预约，但仍应在日志中记录为无效数据并跳过。

排序规则依次为：

1. 已配置时间段按 `time_priority` 的位置排序。
2. 未知时间段排在全部已配置时间段之后，并按开始时间、结束时间升序排列。
3. 同一时间段内，`court_name == PREFERRED_COURT_NAME` 的候选排第一。
4. 其他场地按可解析的场地编号升序排列；无法解析编号时按场地名称和 `place_short_name` 稳定排序。

接口返回顺序不再影响最终选择。原有 `choose_priority_slot()` 和 `choose_salvage_slot()` 的单目标语义由统一排序函数取代；如为了兼容测试保留包装函数，它们只能返回排序结果的第一项。

## 时间阶段

时间表改为：

| 时间 | 阶段 | 响应后的等待间隔 | 行为 |
| --- | --- | ---: | --- |
| 07:28:00–07:32:00 | 预热 | 0.3 秒 | 只查询和排序，不提交，不向下一阶段传递旧候选 |
| 07:32:00–07:35:00 | 核心 | 0.1 秒 | 先探测实际开放；开放后运行动态候选轮次 |
| 07:35:00–07:36:00 | 收尾 | 0.3 秒 | 延续当前开放状态和策略，但使用较慢间隔 |
| 07:36:00–22:30:00 | 全天捡漏 | 10 秒 | 视为已经越过开放窗口，运行动态候选轮次 |
| 22:30:00 以后 | 结束 | — | 正常停止 |

进入核心阶段必须丢弃预热候选，立即执行一次新查询。核心切换到收尾时可以保留尚未开放状态下锁定的目标，但之后使用 0.3 秒间隔。进入全天捡漏时清除锁定目标和本轮失败集合，并开始新轮次。

## 状态机

运行循环维护以下状态：

```text
open_detected: bool
locked_target: candidate | None
attempted_this_round: set[candidate_key]
round_number: int
attempt_number: int
```

### 预热阶段

每次查询后完成排序，只记录候选数量和最高优先候选，不提交预约，也不保存可供核心阶段直接使用的 `warm_candidate`。

### 尚未开放探测

07:32 进入核心阶段后：

1. 立即重新查询。
2. 选择最新结果中的最高优先候选并锁定。
3. 对同一目标调用 `canBook/freeBuyPlace`。
4. 收到 `not_open` 时保持锁定，不加入 `attempted_this_round`，按当前阶段间隔继续探测。
5. 没有候选时按当前阶段间隔重新查询。

第一次出现不属于 `not_open` 的明确预约结果时认为实际开放：

- 成功：保存成功状态并停止。
- `target_unavailable` 或其他明确服务器拒绝：记录 `OPEN_DETECTED`，把当前目标加入本轮失败集合，立即重新查询并进入开放后的动态候选轮次。
- `canBook` 网络异常：不能证明开放，也不算候选失败，保留目标并按当前阶段间隔重试。
- `freeBuyPlace` 发出后的网络或解析异常：继续转换为 `BookingOutcomeUnknown` 并停止，不能据此进入下一候选。

`open_detected` 在单次运行中只能从 `False` 变为 `True`，不能退回。若已经检测到开放后服务器偶尔再次返回 `not_open`，该目标不加入失败集合，按当前阶段间隔重试，但不退回开放前状态。

### 开放后的动态候选轮次

每一轮执行：

1. 查询服务器最新场地状态。
2. 对全部结果重新排序。
3. 跳过 `attempted_this_round` 中已经明确失败的候选。
4. 选择当前最高优先、尚未尝试的候选。
5. 尝试预约。
6. 明确失败时把候选标识加入集合，不等待，立即回到步骤 1。
7. 新查询出现的新候选立即加入当前轮竞争，不必等待下一轮。
8. 最新查询中已经没有任何本轮未尝试候选时，本轮结束；按当前阶段间隔等待，清空集合并开始下一轮。

因此“本轮”不是第一次查询的固定快照，而是从集合清空开始，到某次最新查询找不到未尝试候选为止的动态过程。

## 错误处理

| 结果 | 状态机行为 |
| --- | --- |
| 预约成功 | 写入成功状态，立即停止 |
| `not_open` | 不加入失败集合；保持当前目标并按阶段间隔重试 |
| `target_unavailable` | 加入本轮失败集合；立即重新查询并选择下一候选 |
| 其他明确 `ServerResponseError` | 加入本轮失败集合；立即重新查询，避免卡在同一目标 |
| `canBook` 传输异常 | 不加入失败集合；保持目标并按阶段间隔重试 |
| `freeBuyPlace` 结果未知 | 停止并要求人工核对，不自动重试 |
| Token/登录失效 | 停止 |
| 当日预约次数用完 | 停止 |
| 限流 | 保留当前轮状态，至少退避 5 秒后继续 |
| 查询传输异常 | 保留当前轮状态，按阶段间隔重试查询；限流时使用退避时间 |

异常判断顺序固定为：结果未知、每日上限、尚未开放、目标失效、登录失效、限流、传输异常、其他服务器拒绝。表中的“其他明确 `ServerResponseError`”仅指前述专门分类均未命中的服务器拒绝。

`is_target_unavailable_error()` 必须覆盖日志中出现的措辞，包括：

```text
当前时间段宝地已有用户预约
下手太晚了
请重新选择
```

匹配应优先依赖“已有用户预约”等明确占用语义；“请重新选择”只能作为组合条件，不能单独把所有服务器错误判成场地失效。

## 日志

保留请求耗时日志独立文件，并在事件日志新增稳定、可统计的事件：

```text
PREOPEN | target=...
PREOPEN | not_open | target=...
OPEN_DETECTED | result=target_unavailable | target=...
ROUND_START | round=3
QUERY | round=3 | visible=11 | eligible=10 | skipped=1
TRY | round=3 | attempt=2 | target=...
TARGET_FAILED | round=3 | category=target_unavailable | target=...
ROUND_END | round=3 | attempted=11
```

因为每次失败后都会重新查询，候选总数可能变化，所以日志不使用可能误导的固定 `2/11` 分母；改用轮次、尝试序号、当前可见数、可尝试数和跳过数。服务器原始错误消息仍可进入事件日志，但不得包含 Token、完整学工号或请求参数。

## 请求频率约束

本次保留用户确认的 0.1 秒核心间隔以及四账号独立架构。间隔语义仍是“服务器响应后的等待时间”，不是完整请求周期。

把核心开始时间从 07:29:50 推迟到 07:32:00 会显著降低开放前总请求量，但四账号同时锁定探测仍可能产生较高瞬时请求峰值。现有 5 秒限流退避必须保留，并通过 timing/event 日志继续观察；本版本不增加跨账号全局限流器。

## 测试要求

至少覆盖：

1. 新配置默认包含七档且顺序正确。
2. 旧默认四档自动迁移为七档。
3. 自定义顺序保留并补齐缺失标准时间段。
4. 已知时间优先于未知时间，未知时间按时间排序。
5. 同时间首选场地优先，接口返回顺序不影响选择。
6. 场地编号提供稳定的后续排序。
7. 07:32 边界进入核心，07:35 进入收尾，07:36 进入捡漏。
8. 核心阶段不沿用预热候选，首先重新查询。
9. `not_open` 保持锁定且不加入失败集合。
10. 第一次明确非 `not_open` 结果记录开放并立即重新查询。
11. 失败候选在本轮后续查询中即使再次出现也会被跳过。
12. 新出现候选可在当前轮立即参与。
13. 本轮候选耗尽后等待、清空集合并开始新轮。
14. “当前时间段宝地已有用户预约”被识别为 `target_unavailable`。
15. 查询错误、预检传输错误、限流、登录失效和每日上限保持既定安全行为。
16. 最终提交超时继续停止，不重复提交。
17. 新日志包含开放检测、轮次、动态候选数量和失败分类，且不泄露敏感值。

## 验收标准

- 四账号无需修改 systemd 架构即可使用同一套 v2.4 代码和各自配置。
- 07:32 核心阶段使用新查询结果，不提交预热旧候选。
- 开放前只高频探测一个最高优先目标。
- 开放后每个明确失败目标只在当前轮尝试一次，每次失败都基于最新查询选择下一个目标。
- 下一轮允许此前失败目标重新参与，因此不会永久错过后来释放的场地。
- 成功、结果未知、登录失效和每日上限均保持立即停止的安全语义。
- 全部自动化测试通过，说明文档与实际时间阶段一致。

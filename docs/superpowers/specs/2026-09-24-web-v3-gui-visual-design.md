# Web 第三版：以桌面 GUI 为基准的用户界面改版

## 目标和边界

现有网页版已经具备真实场地查询、手动预约、一次性与每日自动预约、个人资料和独立管理员后台，但用户工作台只借用了 `gui.py` 的蓝色配色，布局与截图明显不同。第三版的目标是让普通用户在桌面浏览器打开场地查询页时，第一眼看到的结构、比例、层级和控件形态与 `jlu_booking/gui.py` 几乎一致，并让其他普通用户页面沿用同一视觉体系。用户提供的 2026-09-24 `gui.py` [参考截图](assets/web-v3-gui-reference.png)（2324×1642）是桌面视觉验收基准；网页保留浏览器自身的窗口外框，窄屏采用可用的响应式布局。

本次以用户前端改版为主，另外把现有“个人设置”升级为“个人中心”，加入本网页账号自己的自动与手动预约记录入口。可增加只读展示查询和页面路由；不改写学校接口、预约核心状态机、任务调度、数据库结构、账号和权限模型。真实查询、手动预约的预检与明确确认、每日计划的启停和先到先得、个人 Token 与同行人隔离、管理员独立后台均沿用现有实现。不得因视觉改版自动开启真实预约或发起预约请求。开发与测试不得调用真实学校预约接口。

## 方案选择

在现有 FastAPI/Jinja 页面、`user_shell.html`、`dashboard.html`、`app.css` 和少量原生 JavaScript 上做统一改版。以 `gui.py` 的颜色、组件形态和信息顺序为设计来源，同时保留现有服务端表单及校验。这比只替换颜色和圆角更能解决“不像 GUI”的问题，也避免引入新的前端框架、构建链和第二套业务状态。

## 共同页面框架

- 普通用户页面使用一套独立于管理员的外框：左侧约 300–320px 蓝色侧栏，右侧白色标题栏和淡蓝灰内容区。桌面宽度足够时，内容在右侧可用空间内展开；不把主内容限制在一个狭窄的固定宽度中。
- 侧栏顶部使用仓库已有吉林大学校徽、中文“吉林大学”和英文 `JILIN UNIVERSITY`，再显示“功能导航”。前两张主导航卡与 GUI 一致，分别是场地查询和自动预约；每日自动预约和个人中心作为同风格的辅助入口保留。当前页使用 GUI 风格的左边标识、底色和状态文字，并提供键盘可见的焦点样式。
- 侧栏“服务场馆”按现有 `api.VENUES` 生成场馆卡，展示该场馆支持的运动项目。当前场馆以绿色边框和标记强调；点击场馆卡会更新查询表单的场馆与项目，并保存用户的场馆偏好。界面不写死场馆、项目或学校接口编码。
- 侧栏底部保留 GUI 的简短校训与数据来源说明。右侧页头显示栏目小标题、页面主标题和真实的当前页面状态；不要用“系统就绪”暗示学校接口已经被实时验证。账号与退出入口应容易找到，但不挤占截图中的主视觉区域。
- 全部普通用户页采用 GUI 的深蓝主色 `#144399`、深色导航卡 `#103A78`、主背景 `#F2F5FA`、正文 `#172033`、边框 `#E3E9F2`、绿色选中态 `#1F9D68`，以及白色方正描边卡片、浅色按钮和紧凑清楚的文字层级。当前网页的大圆角、明显阴影、独立深蓝顶栏与简单文字链接式侧栏需要替换。管理员页面继续使用独立导航，避免用户改版意外改变管理员布局或授权。

### 高保真要求

在与参考截图相同的桌面视口下，去掉桌面原生窗口标题栏后，重点比对左侧蓝色区域和右侧主内容的宽度比例、校徽尺寸与位置、导航和场馆卡的高度及间距、白色标题栏高度、查询卡与四张统计卡的排列、结果卡高度、字体层级、颜色、描边与选中态。第一屏不能新增大幅欢迎语、顶部横幅或状态卡来挤压这些区域。浏览器和 Tkinter 的字形渲染会有细微差别，但主要区域的位置、相对尺寸和内容顺序应高度贴近参考图。实施时生成相同视口的网页截图，与仓库内的参考截图逐轮核对，修正明显偏差后才算视觉完成。

## 场地查询页

桌面端按照截图的自上而下顺序呈现：

1. **快速查询卡片**：右上角当前场馆标签；运动项目采用按钮式单选；日期采用“今天 · 月日 / 明天 · 月日”按钮式单选；右侧为主要查询按钮。场馆由左侧卡片切换，必要的表单值仍正常提交给现有 `/availability/query`。按钮状态与浏览器表单状态同步，服务端继续验证所有输入。无 JavaScript 时仍应有可操作的表单回退方式。
2. **四项摘要**：场馆/项目、查询日期、可预约场地数、可预约时段数。未查询时前两项显示“未查询”，数量显示 0；查询成功后只用本次服务端结果更新。查询失败时明确显示错误，不把旧结果伪装成新结果。
3. **可预约场地卡片**：左侧标题和查询说明，右侧状态与“清空结果”；中间留出与 GUI 类似的宽大结果区域。空态显示“等待查询”。有结果时按场地分组显示真实时段、查询时间和“检查此时段”入口。该入口仍走现有手动预约预检、最终确认与防重复流程。清空结果只清除页面展示，不调用学校接口，也不改变服务器端预约状态。

当前首页的 Token、同行人和每日任务状态卡不再插入上述三层中间。账号准备信息放在自动预约与个人中心页；任务状态放在自动预约相关页，并通过侧栏入口到达。查询页如需显示小型状态，只使用不抢占主布局的页头或卡片角标。

## 其他普通用户页面

- 一次性自动预约、每日自动预约、任务详情、手动预约确认/结果和个人中心都使用同一侧栏、页头、卡片、标签与按钮规范。自动预约相关页面清晰展示账号准备状态、任务配置与执行结果；每日计划页突出当前开关状态、下一执行日、排队名额和关闭后的实际效果。
- 现有所有表单字段、提交目标、CSRF、确认文案、状态提示和日志可达性必须保留。视觉重排不能把“仅扫描”和“真实预约”混淆；真实提交按钮仍需明确标明会向学校系统提交。
- 手动预约结果不明、Token 失效、账号被封、无可用时段、名额耗尽等状态沿用既有语义，以一致的颜色和文本显示，但颜色不是唯一提示。
- 桌面 GUI 的原生窗口标题栏和三个窗口按钮由浏览器提供，网页内容不绘制假系统控件。

## 个人中心与预约记录

`/profile` 升级为“个人中心”，保留并明确呈现当前账号、已脱敏 Token、验证并替换 Token、已验证同行人、验证并保存同行人、修改密码和退出登录。Token 全文仍不进入 HTML、URL、普通 JSON 或预约记录；修改仍调用既有验证及加密保存流程。账号准备状态可从个人中心直接看清。

个人中心新增“我的预约记录”区域，汇总当前网页登录账号的自动任务与已提交的手动预约尝试。每条显示类型、创建/执行或目标日期、场馆、项目、结果状态和查看详情入口；自动记录进入现有 `/tasks/{id}`，该页继续显示经路径保护和脱敏处理的私有运行日志；手动记录进入现有 `/manual/result/{attempt_id}`，展示持久化的提交结果及说明。仅完成预检但没有提交的手动尝试不算预约记录。记录按时间倒序、限制每页数量并分页，避免长期使用后一次加载全部历史。运行日志文件不存在时，仍展示任务状态与“日志暂不可用”，不把缺失日志误判为预约失败。

所有记录查询都以当前登录用户 ID 限定，详情仍经过现有所有权校验；普通用户无法通过改 URL 看其他人的任务或手动尝试。个人中心不纳入服务器上独立运行的旧 CLI 脚本日志，也不提供批量下载 Token 或原始学校响应。管理员既有独立后台和审计流程不受影响。

## 响应式与交互

桌面以提供的 GUI 截图为视觉验收基准；中等宽度允许统计卡片变为两列；手机端折叠侧栏、单列卡片、按钮自动换行，查询与预约操作可在不横向滚动的情况下完成。所有交互使用语义化链接、按钮和表单控件，保留键盘操作、焦点可见、状态文字、错误提示和合适的触控尺寸。场馆与项目联动优先复用现有客户端逻辑，但不以浏览器保存的偏好代替服务端校验；查询结果返回后以实际查询条件为准。

## 验收和交付

- 对照仓库内的 `gui.py` 参考截图检查同尺寸桌面网页截图中的品牌侧栏、场馆卡、白色标题栏、查询卡、四项统计和大结果区；手机端检查导航展开、单列布局及无横向溢出。对其他用户页面检查视觉一致性和现有功能可达性；管理员后台保持独立。
- 用假学校接口和临时状态验证查询表单、场馆/项目联动、摘要数字、空态与错误态、清空结果、手动预约预检链接、各用户页面导航、个人中心 Token 与同行人流程、自动与手动记录的分页和跨用户隔离，以及管理员角色隔离。不得把截图中的示例结果或状态写成真实数据。
- 运行项目现有完整测试、隐私检查、编译检查和 `git diff --check`。开发先在 Mac 本地完成并提交；如后续更新服务器，只部署经过提交和验证的 GitHub 修订，不从未提交工作树部署，也不触碰服务器上无关脚本。
